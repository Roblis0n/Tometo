# 审查

用户要求审查、对抗性审查或处理已有反馈时读取。只读请求保持只读；给出修正方向不等于获得写入权限。本页审的是能够支持结论的行为与证据，而不是按规则数量挑错。

## RV-01 先取得可判断的任务基线

需要原始请求、必要约束、当前版本或差异、适用契约以及相关调用者。只拿到 diff 时，可以判断局部问题，但不能据此宣布满足一份尚未看到的规格。缺失材料影响哪项判断就说明哪项，不用自信措辞补足。

审查深度随工程后果变化，不随文件数机械增长。优先看本次真正触及的行为：正确性、共享数据、权限、资源、失败恢复、兼容性和用户结果。没有影响的领域不强行增加检查项目。

## RV-02 发现要能被定位和处理

一条实质发现说明当前位置、触发输入或状态、具体后果、支撑依据，以及适合当前边界的修正方向。同一根因的多处表现合并说明，不复制成多条“高危”。

严重性由后果、触发条件和暴露范围决定，不由模型标签、措辞激烈程度或报告数量决定。纯偏好、未来假想、已经被现有契约排除的情况，不包装成已成立缺陷。范围外但可能重要的线索明确标为待证，不阻断没有关系的交付。

## RV-03 对抗性审查先攻击结论的依据

选当前最承重的结论，尝试提出能推翻它的具体条件。问现有依据是否可能在错误情况下依旧为真，再追能确认或排除这个条件的位置。证据对象、条件与失效规则以[证据与完成](evidence-and-completion.md)为准。

典型方向包括：运行的是旧版本；观察过滤漏掉实际事件；测试与实现共用错误假设；只验证写入却未验证相应读取；已登记消费者之外还有实际路径；局部修正改变了原目标。它们是追查方向，不是默认已经存在的问题。

不能为了证明审查有效而强行发现 bug，也不能把没有反例当成完整正确证明。没有实质发现是正常结果，交代已审范围及真正影响结论的未知即可。

## RV-04 多人审查要提供不同信息

适合并行时，按不同消费者、假设或证据路径分工，并给所有审查者同一份原始目标和必要事实。可以让他们独立形成解释，不先把主 Agent 的答案设为前提。不要只换“架构／安全／质量”角色名，却让所有人复述同一段摘要。

同一来源、同一复现和同一假设派生的认可不能当独立票数。冲突意见回到对象、版本和触发条件，可能是条件不同，不必强行投票归一。主 Agent 负责核实事实并形成唯一交付，详见[长任务](long-running.md)。

## RV-05 不把成本转移给接收者

提供足够的定位和判别信息，让维护者能理解为什么应处理；不要只扔一段模型猜想、海量日志或没有触发条件的严重标签。建议的修复也要考虑它会否破坏原契约或引入新的问题，不能因问题真实就假定第一种修法正确。

可操作性和缺陷覆盖是两件事：评论容易采纳，不说明抓住了重要缺陷；发现很多问题，不说明每条都有价值。不使用某个研究数据集的百分比估计当前仓库的漏报率。

## RV-06 处理收到的意见

对照最新相关代码和行为，区分仍成立、已修复、前提不符、设计选择、纯偏好与证据不足。合理意见在授权范围内完整处理；不成立的意见用位置和条件说明理由，不为迎合 reviewer 改坏既有语义。

线程关闭、标记 resolved 或评审者认可，只能证明协作状态发生变化；实际修复还要看当前产物。旧版本上的正确意见也可能已不适用。

## RV-07 输出和结束

按实际影响排序，用简洁的“位置—条件—后果—依据—方向”交付成立的发现。必要的待证问题单独标明。不要为每条发现编造数值置信度，或为填满报告添加风格意见。

本地审查、修改、公开发表评论、合并和生产发布是不同动作。未授权的后几项不自动执行。审查范围已覆盖且有价值的发现已说明，就交付；不因零发现而另开无限审查回合。

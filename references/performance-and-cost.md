# 性能与成本

用户提出速度、延迟、吞吐、内存、资源预算或 Agent 执行成本问题时读取。不把每个编码任务变成优化项目，不为了省一次调用牺牲原始目标。

## PC-01 先定义正在优化的结果

区分用户等待时间、后台完成时间、吞吐、资源峰值、总费用和维护成本。用户说“更快”时，优先从现有上下文判断哪条用户路径受影响；只有不同解释会实质改变产品目标，才要求用户选择。

已有性能目标和质量约束沿用，不擅自把尾延迟换成平均值、把端到端耗时换成单函数耗时，或把同质量比较换成删减功能后的比较。没有测量时可以提出结构性判断，但不编造提升幅度。

## PC-02 先找承重路径和资源来源

从当前可用的计时、日志、查询、请求关系和资源记录找串行等待、重复工作、过度扇出、无界缓存或错误生命周期。工具无法观察的部分明确区分，不把“模型认为慢”当成热点证据。

实际涉及队列、扇出或共享服务时，再看在途请求、排队长度、消费者处理能力和重试放大。增加并发可能把等待转成内存或下游压力；沿现有约定限制并发、传播取消、表达背压或负载拒绝。不得通过丢弃用户要求处理的数据、降低质量或秘密改变结果契约来制造吞吐提升；可接受降级须有原授权依据，不自动建设容量平台。

改最影响本次目标的环节，而不按代码看起来复杂与否选择。跨服务扇出、客户端版本差异和第三方延迟可能主导体验；单独优化一个局部实现不自动改善用户路径。运行负载或访问外部服务必须在授权范围内。

## PC-03 对照必须有相同口径

前后比较先说明这次实际改变的对象：代码、运行配置、查询或索引、资源分配、数据布局等都可以是获准的优化对象；记录对应版本或状态，不以“必须改源码”作为成果条件。使任务、数据规模、结果质量及非本次优化因素的运行条件可比；被优化的因素可以改变，其他无法控制的差异要说明，不能把它们的收益归给本次改动。明确预热、缓存、网络及必要收尾的计入方式。只更换统计口径、挑选有利样本，或只在测量时改变环境却未交付相应配置，不能算完成优化；合法改变运行条件且有对应依据时，应按实际改变的对象报告收益与资源、费用代价。更快但错误率或资源峰值越过原约束，也不是完成原任务。

测量有噪声时，可按[长任务](long-running.md)有界重复取样并报告实际口径，不只挑最快成功样本，也不用一个样本宣布普遍收益。

轻量负载生成器可以回答协议吞吐或连接压力，但不能冒充完整浏览器行为；离线记录可以解释已发生的现象，但不能自动证明当前生产改进。只取得局部结果，就只宣称局部结果。

## PC-04 先减少无效工作，再考虑增加并行

重复检索、无效重试、反复加载全文、过量工具定义、重复评审和冲突集成会消耗成本。优先消除这类不改变决定的工作，保留关键前提、反例和原始结果定位。少输出不等于删掉有用证据，少思考也不一定减少总回合。

并行只有在工作可独立、资源允许且集成成本可控时才增加收益。多个 Agent 等同一服务、争同一文件或反复查同一根因，可能更慢更贵。按[长任务](long-running.md)处理，不设置固定代理数。

## PC-05 成本按完整任务计算

考虑模型调用、工具时间、重新执行、环境资源、集成、人工解释和后续维护，而不只看每 token 单价或单次生成速度。已有预算是约束；需要更多实际费用时，遵守用户授权。

不能凭其他工程师的成本百分比推导本项目收益，也不能把某项公开基准成绩当作当前任务的成功率。没有本项目数据时，说明选择理由和未知，不捏造节省比例。

## PC-06 优化与完成不互相替代

用户要完整实现时，成本优化以不降低目标为前提；用户只要分析时，不擅自启动耗费资源的大规模运行。达到既定目标且已无影响交付的实质问题，就交付，不继续追求没有预算和使用价值依据的极限指标。

发现慢的根因是工具或项目结构时，可以在本次获准范围修正最相关的入口；不把一次性能任务升级成全站可观测平台、长期基准平台或自动模型路由系统。
